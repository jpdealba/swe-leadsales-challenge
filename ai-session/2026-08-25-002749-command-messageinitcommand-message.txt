  A. Errors the flow needs that have no class

  1. Lead not found on move. MoveLeadToStage's JSDoc says "The lead must exist
  in the funnel" — but the README's Part 1 list for that use case names only
  three validations (stage exists, capacity, transition), and there is no
  LeadNotFoundError. The gap is real and it's the one asymmetry between the
  code's comments and the README.
  - Recommend: add LeadNotFoundError as a fifth error class, matching the other
    four's shape — it's a distinct business outcome and a caller must be able to
    tell it apart.
  - Risk of the alternative: reusing InvalidStageTransitionError (its free-form
    message makes it tempting) conflates "your lead doesn't exist" with "that
    move isn't allowed", which an HTTP adapter would map to 404 vs 409 — one
    error class means one wrong status code forever.

  2. Nothing distinguishes "stage exists but is full" at add-time vs move-time.
  Both paths throw StageCapacityExceededError(stageId).
  - Recommend: keep one class — the stage id is enough context, and the caller
    knows which operation it invoked.
  - Risk of the alternative: separate add/move capacity errors doubles the error
    surface for zero caller benefit, and the README explicitly folds both under
    rule 3.

  ---

  B. Cases the four rules don't cover

  3. Order of validation when several rules fail at once (e.g. move a lead to a
  nonexistent stage that is also its current one, or to a stage that is both
  full and its current stage). Rules 2–4 are listed but not ordered.
  - Recommend: existence → same-stage → capacity, and document it; a stage that
    doesn't exist can't be reasoned about, and rule 4 is a cheap identity check
    that shouldn't be masked by a capacity count.
  - Risk of the alternative: checking capacity before rule 4 means a lead
    sitting in a full qualified gets StageCapacityExceededError when asked to
    move to qualified — a nonsense message the reviewer will pounce on.

  4. Backward moves (Closed → New). Rule 4 forbids only same-stage; Part 2 §4
  says "one customer forbids backward moves", implying today they're permitted.
  - Recommend: allow them, and state the assumption — the evolution question
    only makes sense if the default is permissive.
  - Risk of the alternative: forbidding them invents a fifth rule, and it
    silently answers Part 2 §4 in the code, removing the thing you're supposed
    to discuss.

  5. Skipping stages (New → Closed directly). Not addressed at all.
  - Recommend: allow — the funnel is an ordered board, not a state machine, and
    nothing in the rules says adjacency.
  - Risk of the alternative: enforcing adjacency makes the qualified capacity-2
    fixture nearly untestable and imposes a rule no customer asked for.

  6. Multi-funnel scoping. Rule 1 says "twice in a funnel", but
  findByPhone(phone) takes no funnel id and there is no FunnelRepository.
  - Recommend: treat one repository instance as scoped to one funnel, and say so
    — the constructor injection of Funnel into both use cases already assumes
    it.
  - Risk of the alternative: adding a funnelId parameter to the repository
    expands the given interface for a requirement the test never states, and
    you'd still have no way to load a second funnel.

  7. Idempotent / repeated operations — adding the same lead twice is rule 1,
  but re-issuing the same move (already applied) is just rule 4.
  - Recommend: let rule 4 handle it; no special idempotency key.
  - Risk of the alternative: building idempotency now is speculative
    infrastructure and pre-empts the concurrency discussion in Part 2 §1.

  8. No createdAt on Lead — yet Part 2 §3 asks for "the first 50 leads of each

  Question 6 of ~8 — What order do the four checks run in, and does the first 
  failure win?

  The README lists rules 2, 3 and 4 but never orders them, and now there's a
  fourth check in front. Order is observable behavior: when a request violates
  two rules, the order decides which error the agent sees.

  Three scenarios that pin it down:

  1. A lead sitting in a full qualified is moved to qualified. Capacity-first
     says StageCapacityExceededError — "that stage is full" — when the honest
     answer is "the lead is already there." Rule-4-first says
     InvalidStageTransitionError. The second is plainly correct, and note the
     fixture gives qualified capacity: 2 precisely so this is reachable.
  2. An unknown phone moved to a misspelled stage id. Lead-first reports the
     missing lead and hides the typo; stage-first reports the typo and hides
     that the lead never existed.
  3. A lead moved to a stage that doesn't exist. Nothing else can be evaluated —
     you can't ask whether a nonexistent stage is full or is the current one.

  My recommendation: lead exists → target stage exists → rule 4 (same stage) → 
  capacity, fail-fast on the first violation.

  The ordering principle: existence before state, identity before counting. You
  can't reason about a stage you can't resolve, and you shouldn't count
  occupants of a stage the lead is already in. Capacity goes last because it's
  the only check that depends on repository contents rather than on the request
  itself — it's also the most expensive and the one that's racy under
  concurrency, which sets up Part 2 §1 nicely.

  That order also makes scenario 1 come out right, and it dissolves a question
  I'd otherwise have to ask you: does the moving lead count against its own 
  target's capacity? With rule 4 checked first, source and target can never be
  the same stage by the time capacity is evaluated, so the self-counting case is
  unreachable. No special handling needed.

  The trade-off: fail-fast reports one problem at a time. An agent fixing a
  request with two faults gets two round-trips. Aggregating all violations into
  one error would be friendlier — but execute returns Promise<void> and signals
  by throwing, so aggregation means inventing a composite error type with a list
  of failures, which is a bigger deviation from the given design than the
  friendliness is worth. Fail-fast is also what the four single-purpose error
  classes are shaped for.

  The lead-before-stage choice in scenario 2 is the genuinely arguable one.
  Stage-first has an argument: the stage list is funnel configuration the agent
  can see on screen, so a bad stage id is a caller bug worth surfacing first. I
  still prefer lead-first — the lead is the subject of the sentence "move this 
  lead to that stage", and a missing subject makes the rest moot.

  Take that order, or do you want stage existence checked before the lead?
